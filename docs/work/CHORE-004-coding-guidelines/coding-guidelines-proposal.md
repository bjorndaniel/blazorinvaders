# Coding guidelines proposal

Sources I read: `src/.editorconfig`, `global.json`, all four `.csproj` files, `.github/workflows/deploy.yml`, `.gitattributes`, `docs/architecture.md` (A1-A23), `README.md`, all of `src/api`, most of `src/core` (`GameEngine.cs`, `SceneBuilder.cs`, `Scene.cs` and 11 GameObjects files), `src/Pages/*.razor`, `src/Components/SetHighScore.razor`, `src/wwwroot/js/game.js` and `effects.js`, and 6 of the 9 test files. The repository has no `CONTRIBUTING.md`, no `CLAUDE.md` and no copilot instructions. `AGENTS.md` only describes the DevAgents workflow.

The rules below leave out what `docs/architecture.md` already covers: the pure core (A10), the module layout (A11), "C# describes, JS draws" (A12), validation in `HighScoreValidator` (A20), the API's logging and error answers (A23), and the configuration rules (A22).

| Errors and logging | API: one try/catch per function. Expected failures come first as filtered catches (`catch (RequestFailedException ex) when (ex.Status == 404)`, `GetHighScore.cs:36`), then a catch-all that logs with `ILogger<T>` and answers in plain text (A23). Untrusted input is validated with `bool TryX(..., out result, out string error)` and never by throwing (`HighScoreValidator`). Core: there is no `throw` anywhere. Unexpected states return early (`if (_player == null) return;`). Client: the HTTP, interop and localStorage boundaries catch errors and keep the game playable, writing a one-line message with `Console.Error.WriteLine` for failures and `Console.WriteLine` for expected offline cases (`Index.razor:216-275`). The fire-and-forget `_ = SubmitHighScoreAsync()` (`Index.razor:222`) relies on that method catching everything itself. JS: `try { ... } catch { return null; }` around localStorage, with a comment at `game.js:93`, and `.catch(e => console.error(e))` on the frame call. | **CG20 (must)**: no empty or silent catch. A catch logs (an API `ILogger` in the API; the console in the client and in JS) or carries a comment saying why ignoring the error is safe. **CG21 (must)**: catch specific, expected exceptions first (`catch (X) when (...)`). A catch-all is allowed only at a boundary: a Function's `Run`, a Razor handler, a JS-interop call, or a fire-and-forget task. **CG22 (should)**: validating untrusted input returns `bool Try...(..., out T result, out string error)` with a short message the user can read; no exceptions for validation. **CG23 (must)**: `_ = SomethingAsync()` only for a method that catches all of its own exceptions, with a comment saying so. **CG24 (must)**: never log or return the connection string, environment values or an exception's text in an HTTP response (client console messages may include `ex.Message`). **CG25 (should)**: core code handles expected game states with early returns, not exceptions. | Use `ILogger<T>` in the client instead of `Console` (Blazor WASM's logger writes to the browser console), as one way for the whole client. |

| Data, types and state | Nullable reference types are on in every project. `!` appears where an invariant holds locally (`_boss!` in `HitBoss`, `_module!` after `start`, `score.Day!` after validation, `engine.Player!` in tests), and `default!` is used for Blazor parameters. Randomness is injected (`GameEngine(int, int, Random?)`) and split into one seeded stream per subsystem (`GameEngine.cs:45-49`), so every player gets the same daily game. The clock comes in as frame timestamps. `DateTime.UtcNow` appears only in convenience overloads and factories that call an overload taking the date (`HighScoreValidator.cs:26, 95-99`; `DailyChallenge.Today()`). Dates are UTC; keys are `yyyyMMdd`, formatted with `CultureInfo.InvariantCulture` (`DailyChallenge.cs:24`, `SceneBuilder.cs:75`; fix commit 8883614). `Leaderboard.razor:26` leaves the culture out (harmless only because the client sets `InvariantGlobalization`). Value types are records (`GameEvent` is a `readonly record struct`; `DailyChallenge` and `HighScoreRequest` are records). Collections are exposed as `IReadOnlyList<T>`, with `private set`/`internal set`, and `Scene` uses `required init`. The Blazor page implements `IAsyncDisposable`, checks `_disposed` after awaits that can outlive it (`Index.razor:86, 245`) and disposes the JS module and the `DotNetObjectReference`. There is no `async void` and no `.Wait()`. | **CG30 (should)**: use `!` only where the reason it is non-null is visible in the same method or is a documented invariant; otherwise use a null check or a pattern (`is { } x`). **CG31 (must)**: core logic never calls `new Random()` or reads the clock directly. Randomness comes from the injected `Random` (a separate seeded stream per subsystem, if a new subsystem draws numbers), and time comes from the timestamps passed in. `DateTime.UtcNow` is allowed only in a convenience overload that calls one taking the date. **CG32 (must)**: dates and times are UTC. Formatting and parsing of dates and numbers that are stored, sent or used as keys uses `CultureInfo.InvariantCulture` and the existing formats (`yyyyMMdd` for keys). **CG33 (should)**: small value types are records; public collections are `IReadOnlyList<T>`; setters are as narrow as possible (`private set`, `internal set`, `init`). **CG34 (must)**: no `async void`, `.Result` or `.Wait()` on tasks.
