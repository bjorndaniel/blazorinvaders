# Architecture proposal: CHORE-003

Existing code, no change requested: each suggestion records what the code already uses.

| Area | Suggestion | Why | Alternatives |
|------|------------|-----|--------------|
| Language and runtime | C# on .NET 10 (SDK 10.0.200 via `global.json`, `rollForward: latestFeature`) for client, core and tests; API stays on .NET 9 (`net9.0`, Functions runtime `--runtime-version 9`) | What the code uses; the API follows the Functions runtime that `provision.yml` sets up | Move the API to `net10.0` and runtime 10 (one stack, CI drops the 9.0.x SDK; needs a Function App setting change) |
| Architecture pattern | Modular monolith with a pure core: game rules (`GameEngine`) and the scene description (`SceneBuilder` -> `Scene`) live in `src/core` with no Blazor or browser dependency; the UI and the API are thin shells around it | Keeps the game logic unit-testable and the renderer replaceable (`core/BlazorInvaders.Core.csproj` comment) | Hexagonal with explicit ports (more ceremony than a game needs); all logic in Razor components (untestable) |
| Modules | `src/core` (rules, game objects, scene), `src` (Blazor WASM client: pages, components, JS interop), `src/api` (Azure Functions), `tests/BlazorInvaders.Tests` (one xUnit project). Dependencies: client -> core; tests -> core and `HighScoreValidator.cs` (compiled in); API independent | What the code uses; the API shares no assembly with the client | Shared contracts project for `HighScore`/`HighScoreRequest` used by client and API |
| Web or API framework | Azure Functions v4, isolated worker (`Microsoft.Azure.Functions.Worker` 2.51.0, HTTP extension 3.3.0, `HttpRequestData`/`HttpResponseData`), one class per endpoint, anonymous HTTP triggers | What the code uses; serverless, pay-per-use, fits a small leaderboard API | ASP.NET Core integration for Functions (`ConfigureFunctionsWebApplication`); SWA managed functions |
| UI framework | Blazor WebAssembly 10.0.4 (standalone, PWA with service worker for offline play), Bootstrap CSS, Blazored.Modal 7.3.1; game drawn on an HTML5 canvas by ES modules (`wwwroot/js/game.js`, `effects.js`) that execute the C# `Scene` draw commands; JS owns the frame loop, input, audio and `localStorage` | Layout and rules stay in C#; JS does only what needs the browser; constants shared across the boundary are marked "Must match" | Draw from C# via a canvas interop library (slower per frame); Blazor Server (no offline play) |
| Data storage and access | Azure Table Storage via `Azure.Data.Tables` 12.9.1, table `HighScores`, partition per board (`HighScore`, `Daily-yyyyMMdd`), created on first use; no ORM, no migrations; Azurite locally. Client-side: `localStorage` for personal bests and pending scores | What the code uses; cheapest store for a top-10 list, schemaless | Cosmos DB (Table API or NoSQL); Azure SQL with EF Core (overkill) |
| Validation | Server-side, in the dependency-free static `HighScoreValidator` (bounded body read, `System.Text.Json`, generated regexes, score and day ranges); endpoints call it before storage | One unit-tested place for every rule on untrusted input | DataAnnotations or FluentValidation (a new dependency for a handful of rules) |
| Authentication | None: anonymous players identified only by 1-3 initials; Functions use `AuthorizationLevel.Anonymous`; access limited by CORS to the site's origins (`provision.yml`, `set-custom-domain.yml`) | An arcade leaderboard with no accounts | SWA built-in auth (GitHub/Microsoft login) to deter fake scores; Function keys (cannot be secret in a WASM client) |
| Configuration and secrets | Client: `wwwroot/appsettings.json` key `FunctionsApi`, placeholder replaced by CI from the `FUNCTIONS_API_URL` secret, `appsettings.Development.json` (git-ignored) locally. API: environment variable `AzureWebJobsStorage` (Function App setting; `local.settings.json`, git-ignored, locally). Deployment credentials only in GitHub secrets | What the code uses; no secret ever reaches the client bundle | Typed options via `IOptions<T>`; Key Vault references for the storage connection string; managed identity instead of a connection string |
| Logging and errors | API: injected `ILogger<T>` logs exceptions; responses are plain-text status messages without exception details (400/413/500). Client: failed API calls degrade gracefully (game stays playable offline, scores queued) | Errors stay out of responses; offline play is a feature | Application Insights worker package for telemetry; ProblemDetails JSON errors |
| Testing | xUnit 2.9.3 unit tests in `tests/BlazorInvaders.Tests` against core and `HighScoreValidator`, deterministic via seeded `Random` and fed timestamps, `InternalsVisibleTo` for state setup; coverlet collector. No integration, component or end-to-end tests | Rules and validation carry the risk; Razor, JS and storage code is kept thin | bUnit for Razor components; Playwright end to end; Testcontainers with Azurite for the Functions |
| Linting and formatting | `src/.editorconfig` (underscore-prefixed private fields, expression-bodied members, `Async` suffix; severities suggestion), nullable reference types and implicit usings enabled; no analyzers, no JS linter, no format check in CI | What the repo has | Root `.editorconfig` covering tests too, plus `dotnet format --verify-no-changes` in CI; `TreatWarningsAsErrors` |
| Build, CI and deployment | GitHub Actions `deploy.yml`: build client and API, run tests on push and PR to `master`; on push publish the WASM app to Azure Static Web Apps (Free) and the API to a separate Function App (consumption plan). Infrastructure by `provision.yml` and `set-custom-domain.yml` (manual, `az` CLI) | What the repo uses | Bicep or Terraform instead of `az` scripts; the API as SWA managed functions (one deployment, no CORS) |

## Observations (not proposals)
- `SaveHighScore.cs` at the repository root is a stale in-process Functions template (Newtonsoft, `Microsoft.Azure.WebJobs`); no project compiles it.
- `src/wwwroot/routes.json` (legacy SWA routing, superseded by `staticwebapp.config.json`) and `src/wwwroot/sample-data/weather.json` are template leftovers.
- `src/.editorconfig` does not cover `tests/`.
